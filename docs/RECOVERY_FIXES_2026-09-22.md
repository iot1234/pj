# การแก้จุดติดขัดและป้องกันทำซ้ำ — 22 กันยายน 2026

ขอบเขต: PHP/MySQL เท่านั้น ไม่มีการแก้ newap หรือเพิ่ม manual-paid endpoint

## บัญชีพร้อมเพย์

- เปลี่ยน/ลบบัญชีไม่ได้ถ้ายังมีคำสั่งโอน reserved ที่ใช้บัญชีอื่น ระบบคืน `PROMPTPAY_HAS_RESERVED_BILLS` และไม่บันทึกฟิลด์อื่นในคำขอเดียวกันด้วย
- ข้อความระบุเลขบิลและรอบที่เกี่ยวข้องบางส่วน ปุ่มแนะนำพาไปหน้าบิล ให้ตรวจสถานะการรับเงินจริงและจัดการรายการเดิมก่อนกลับมาเปลี่ยนบัญชี
- การแก้ชื่อแสดงผลหรือบันทึกบัญชีเดิมยังทำได้ ยอดโอนที่จองแล้วและ snapshot เดิมไม่เปลี่ยน
- หากการตั้งค่าถูกแก้ผิดนอกระบบ การคืนบัญชีให้ตรงกับคำสั่งโอนค้างทั้งหมดทำได้ ถ้ามีหลายบัญชีปะปนกัน ต้องตรวจหลักฐานรายบิล ไม่สุ่มใหม่ ไม่ล้างคำสั่งโอน และไม่ตั้ง paid เพื่อข้ามข้อจำกัด
- การล็อกแถว settings ป้องกันการเปลี่ยนบัญชีแทรกระหว่างการจองยอด ใช้ current read ของคำสั่งโอนโดยไม่ล็อก bills ย้อนลำดับ

## สลิปในแชต LINE

- รูปสลิปและข้อความที่ขึ้นต้น `แจ้งชำระ ` ไม่ถูกตัวกรองข้ามแล้ว บอทตอบว่าต้องให้ผู้ดูแลตรวจยอดรับจริง เว็บยังไม่ได้รับไฟล์จากแชต และไม่ต้องโอนซ้ำ
- ยังคงตรวจลายเซ็น OA ปลายทาง จำกัดจำนวนตอบ และป้องกันตอบ event เดิมซ้ำ
- ข้อความคุยทั่วไปไม่ทำให้บอทตอบแทรก
- การตอบนี้ไม่ใช่การรับรองเงินเข้า ไม่สร้าง payment และไม่เปลี่ยนบิลเป็น paid การตรวจสลิปอัตโนมัติยังต้องมี provider ที่ตั้งค่าถูกต้อง

## คิว QR หลังแก้ APP_URL

- หากคำขอแรกถูกปฏิเสธในการตรวจข้อมูลก่อนส่ง และยังไม่มีการเรียก LINE เลย ระบบคงสถานะ failed แต่คืน attempts เป็น 0 เพื่อระบุว่าไม่เคยเริ่มส่ง ผู้ดูแลกดเข้าคิวใหม่ได้โดยใช้ URL ปัจจุบันและยอดจองเดิม
- หากเคยเริ่มส่ง มี timeout, worker เคยล้ม, มี claim ก่อนหน้า หรือเกิด database retry หลังเริ่มส่งแล้ว จะไม่คืนค่าเป็น unattempted
- คำขอที่อาจถึง LINE แล้วเก็บ payload และ retry key เดิม หากข้อมูลนั้นใช้ต่อไม่ได้ การเข้าคิวจะปฏิเสธด้วย `LINE_DELIVERY_RECONCILIATION_REQUIRED` แทนการแจ้งว่าเข้าคิวสำเร็จแล้วล้มเหลวซ้ำ
- ให้ตรวจประวัติการส่งก่อน ผู้พักยังพิมพ์ `บิล` เพื่อขอข้อมูลล่าสุดได้ ห้ามสร้างข้อความส่งซ้ำเองโดยไม่ทราบผลเดิม
- งาน failed เก่าที่มี attempts มากกว่า 0 ไม่สามารถสรุปย้อนหลังว่าไม่เคยส่งได้ จึงไม่ถูกย้ายเข้ากลุ่มสร้างใหม่โดยอัตโนมัติ

## สถานะส่งและคำแนะนำผู้พัก

- หน้าบิลคำนวณสถานะจาก binding/OA/ผู้รับปัจจุบันเท่านั้น ประวัติ binding เก่ายังเก็บอยู่และแสดงจำนวนแยก ไม่ลบทิ้ง
- ความล้มเหลวของ binding ที่ถอนแล้วไม่ทำให้ worker health มีจำนวน failed เกินจริง
- ข้อความรับเข้าพักและเปลี่ยนเบอร์ตรงกับ phone-only login ไม่สัญญาว่าจะมี activation code หรือต้องตั้งรหัสผ่าน
- แจ้งผลของการเปลี่ยนเบอร์อย่างชัดเจนว่าเซสชันและการผูก LINE เดิมถูกยกเลิก ต้องผูก LINE ใหม่
- สถิติที่เคยเป็นรอ activation เปลี่ยนเป็นจำนวนผู้พักที่ยังขาดเลขมิเตอร์เริ่มต้น

## การทดสอบ

Regression ใหม่อยู่ใน `tests/line_payment_qr_mysql.php`, `tests/transfer_instruction_mysql.php` และชุด JavaScript ของ bill status, recovery guidance, resident phone login รวมทั้ง source contracts เดิมที่ปรับให้ตรงกับ semantics ของการส่งที่ยังไม่เคยเริ่ม

ผลยืนยันรอบสุดท้าย: PHP 127 ผ่าน, JavaScript 219 ผ่าน, MySQL 18 suites / 253 groups ผ่าน (LINE QR 23, transfer 16), PHP lint 96 ไฟล์, LINE bot 8 และ monthly billing CLI 7 ผ่าน ตรวจ schema 54 รายการผ่านพร้อมคำเตือนการตั้งค่าของ fixture 2 รายการ และ install.sql ยังตรงกับ schema เดิม

เบราว์เซอร์ทดสอบจริงกับ PHP/MySQL แยก: หน้าผู้ดูแล 11 ส่วน, การป้องกันข้อมูลเก่าเมื่อโหลดล้มเหลว, จองแล้วคำตอบเครือข่ายหาย/กดใหม่ไม่สร้างซ้ำ, รับเข้าพักด้วยข้อความ phone-only ที่แก้แล้ว, กลับไปเติมมิเตอร์จากหน้าบิล, กดออกบิลซ้ำได้บิลเดียว, ผู้พักอ่านได้เฉพาะบิลตนเอง, QR เมื่อปิด provider, ยอดของสามห้องไม่ซ้ำและคงเดิมเมื่อโหลดซ้ำ, และ layout ที่ 320/390/768/1366px ทั้งหมดผ่าน ไม่มี JavaScript errors หรือคำขอไปผู้ให้บริการจริง

ทุกการทดสอบ provider ใช้ transport จำลอง ฐานข้อมูลเป็น fixture แยก ไม่มีการส่ง LINE หรือโอนเงินจริง การผ่านชุดทดสอบไม่แทนการตรวจ public HTTPS, Apache/CDN และการแสดงผลในแอป LINE จริงก่อน deploy

การแก้รอบนี้ไม่เปลี่ยน schema และไม่ต้องเพิ่ม migration
