# ตรวจความถูกต้องและความปลอดภัยของการชำระเงิน — 21 กันยายน 2026

ผลตรวจเพิ่มเติมวันที่ 22 กันยายน รวม QR/LINE, ทุกฟีเจอร์หลัก และ browser integration
อยู่ใน [FEATURE_AUDIT_2026-09-22.md](FEATURE_AUDIT_2026-09-22.md)
จำนวนด้านล่างเป็นผลของรอบตรวจวันที่ 21 ไม่ใช่จำนวนล่าสุด

ขอบเขต: PHP/MySQL ใน `php-mysql` — บิล, จองยอดพร้อมเพย์, อัปโหลดสลิป,
ตรวจสลิป, ตรวจซ้ำ/ปิดรายการ, หน้าผู้พักและผู้ดูแล และความสัมพันธ์กับการแจ้งบิล LINE

## จุดที่แก้

- **ส่งสลิปแล้วเน็ตขาด:** ซ่อนและยกเลิกการแสดง QR เดิมตั้งแต่เริ่มส่งสลิป
  อ่านสถานะจากเซิร์ฟเวอร์กลับ เก็บไฟล์ที่เลือกไว้เมื่อล้มเหลว และไม่เปิด QR
  หากยังยืนยันผลไม่ได้ มีปุ่มตรวจสถานะอีกครั้ง ไม่ส่งคำขอชำระซ้ำอัตโนมัติ
  ตัวบันทึกคำขอที่ยังไม่ทราบผลอยู่ใน `sessionStorage` เพื่อรองรับการรีเฟรชระหว่างส่ง
  โดยเก็บเฉพาะเลขบิล ไม่เก็บรูปหรือข้อมูลธนาคาร หากเบราว์เซอร์ปิด storage
  จะยังมีตัวป้องกันในหน่วยความจำสำหรับหน้าที่เปิดอยู่
- **ผลสำเร็จไม่ตรงข้อความ:** แยกข้อความชำระสำเร็จ / รอตรวจ / ปฏิเสธ
  ตามผลจริง และไม่แสดงคำสั่งให้โอนสำหรับรายการที่บันทึกการชำระแล้ว
- **บัญชีรับเงินเปลี่ยนหลังจอง QR:** แจ้งว่าคำสั่งโอนเดิมมีข้อขัดแย้งและซ่อน QR
  สลิปที่รับไว้แล้วคงเป็น pending พร้อมเหตุผล ไม่ตอบเหมือนอัปโหลดล้มเหลว
  ไม่เรียกผู้ให้บริการเมื่อรู้อยู่แล้วว่าบัญชีขัดแย้ง
- **ตรวจขั้นสุดท้าย:** ตรวจยอดจริงและ fingerprint การตั้งค่าซ้ำสำหรับทั้งบิลที่จอง QR
  และบิลเก่าที่ไม่มีรายการจอง ก่อนเปลี่ยนสถานะเป็นชำระแล้ว
- **หน้าผู้ดูแล:** ล้าง/ล็อกรายการเก่าระหว่างโหลดใหม่ ป้องกันผลตอบกลับหรือข้อผิดพลาด
  จากตัวกรองเก่าทับข้อมูลใหม่ ป้องกันโหลดหน้าซ้ำ และล็อกการตรวจซ้ำ/ฟอร์มปิดรายการ
  ระหว่างส่ง พร้อมอ่านสถานะกลับหลังคำขอล้มเหลว
- **ไฟล์และการรีเฟรช:** ป้องกันไฟล์ว่าง ล็อกตัวเลือกไฟล์ระหว่างส่ง
  หยุด background refresh จากการแทรกฟอร์มที่กำลังส่ง และปล่อย GD object
  โดยไม่เรียก `imagedestroy()` ที่ deprecated ใน PHP 8.5

## ผลทดสอบ

ใช้ PHP 8.5.8, Node และ MySQL 8.4.10 แบบ disposable บน loopback
ชุด integration ใช้บัญชี runtime ที่มี SELECT/INSERT/UPDATE และ schema แยกกัน
ไม่มีการเชื่อมต่อฐานข้อมูลจริงหรือส่งภาพไปยังบริการตรวจสลิปจริง

- PHP unit/contract: **125 ผ่าน**
- JavaScript interaction/contract: **171 ผ่าน**
- Payment MySQL: **19 กลุ่มผ่าน**
- Transfer reservation MySQL: **10 กลุ่มผ่าน**
- Billing/LINE delivery MySQL: **33 กลุ่มผ่าน**
- Health/readiness MySQL: **10 กลุ่มผ่าน**
- Lifecycle MySQL: **1 กลุ่มผ่าน**
- Schema audit: **54 ผ่าน**, ไม่มีข้อไม่ผ่าน; มี 2 คำเตือนจาก fixture lifecycle
  ที่ไม่ได้ตั้งบัญชี PromptPay/ผู้ให้บริการตรวจสลิป ไม่ใช่ผลตรวจ configuration production
- PHP syntax, JavaScript syntax และ `git diff --check` ผ่าน

กรณีสำคัญที่ทดสอบ: สตางค์ที่จองไว้ตรงยอดจริง, บิลไม่ถูกบวกส่วนต่าง,
อัปโหลดไฟล์เดิมหลัง paid ได้ผลเดิมโดยไม่เรียก provider ซ้ำ, ส่งพร้อมกันทั้งไฟล์เดียวกัน
และคนละไฟล์, สลิป/เลขอ้างอิงซ้ำข้ามบิล, สิทธิ์ผู้พักคนละบิล, ไฟล์ไม่ถูกต้อง,
provider timeout/ข้อมูลไม่ครบ/แจ้งสลิปซ้ำ, ยอดผิด/เวลาอนาคต, เปลี่ยนการตั้งค่าระหว่างตรวจ,
rollback เมื่อ audit ล้มเหลว, ผลตรวจเก่าหลัง lease ถูกแทนที่, ไฟล์หลักฐานถูกแก้,
การปิดรายการไม่เปลี่ยนบิลเป็น paid และปิด provider แล้วต้องไม่รับคำขอใหม่

เพิ่ม `tests/payment_mysql.php` เข้า CI เดิม พร้อม regression tests ฝั่ง JavaScript
สำเนาจาก `git archive` บน Windows แปลง LF เป็น CRLF ทำให้ source-string tests
เดิม 3 ข้อล้มเหลวหลอก; ยืนยันว่าเนื้อหาเหมือนกันเมื่อ normalize และทดสอบไฟล์
workspace ที่รักษา line endings แล้วผ่าน ไม่ได้ลดข้อกำหนดของ tests เหล่านั้น

## ข้อจำกัดและสิ่งที่ต้องตรวจบน staging

- การเปิด QR หรือส่งรูปในแชต LINE **ไม่ใช่การยืนยันการรับเงิน**
  LINE fallback เปิดแชตพร้อมเลขบิลเท่านั้น ไม่ได้นำรูปเข้าระบบตรวจสลิป
  และไม่มีการตัดบิลอัตโนมัติจากแชต หากต้องการตัดบิลอัตโนมัติให้ตั้ง
  SlipOK/EasySlip และส่งสลิปผ่านเว็บ
- รายการ pending ที่ผู้ให้บริการแจ้ง duplicate หลังขาดการเชื่อมต่อยังต้องตรวจสอบ
  กับผู้ดูแล ไม่ควรปิดทิ้งหรือบอกให้ผู้พักโอนใหม่โดยยังไม่ตรวจยอดธนาคาร
  ไม่ได้เพิ่มช่องทางอนุมัติเงินด้วยมือหรือเปลี่ยนนโยบายหลักฐานถาวรในการแก้ครั้งนี้
- ทดสอบ provider แบบจำลอง จึงยังต้องทดสอบบัญชีรับเงินจริง, credential/โควตา,
  QR กับแอปธนาคาร และการตอบกลับของ provider บน staging ก่อนเปิดใช้งานจริง
- ทดสอบ interaction ด้วย Node/VM; ไม่ได้อ้างว่าได้ทดสอบภาพหน้าจอทุกเบราว์เซอร์
  หรือการโอนเงินจริง ไม่แก้ข้อมูล production และไม่มี migration ใหม่
