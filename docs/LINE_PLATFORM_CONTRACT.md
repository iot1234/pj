# LINE admin platform implementation contract

Internal implementation contract for the expanded admin LINE request (2026-09-15). The existing single-OA configuration and existing verified residents remain valid as OA `0`; additional OAs have positive IDs. Default selection applies to new invitations and never changes an existing recipient's OA. Admin and owner roles may manage LINE through the dedicated routes; payment settings and user administration retain their existing permissions.

## Storage

1. `line_official_accounts`: manually allocated bigint `id` (0 is reserved legacy), `slug` unique varchar40, `name` varchar120, `description` varchar500 nullable, `basic_id` varchar33 nullable, `channel_id` varchar60 nullable, `add_friend_url` varchar255 nullable, `access_token_enc` text nullable, `channel_secret_enc` text nullable, `enabled` bool, `is_default` bool, `route_token` char48 unique (hex), `provider_user_id` varchar33 nullable unique, `token_fingerprint` char64 nullable, `identity_verified_at`, `last_seen_at`, `last_error` varchar100 nullable, `deleted_at`, `created_by`, `updated_by`, timestamps. Unique generated default key for nondeleted default. Seed id0 with metadata only; its Basic ID/token/secret are read from integration_settings. New secret AAD includes OA ID. Slug is a label; webhook uses random route_token.
2. `line_room_bindings`: auto bigint `id`, `resident_id`, `occupancy_id`, `auth_version`, `oa_id` FK including0, `code_hash` char64 unique, `code_enc` text nullable, `status` pending/bound/expired/revoked, `line_user_id` varchar33 nullable, `proof_hash` char64 nullable, `expires_at`, `bound_at`, `revoked_at`, `created_by` nullable, timestamps. Generated `active_line_user_id` only when bound; UNIQUE(oa_id,active_line_user_id). Multiple pending codes allowed. Relationship guard ensures occupancy belongs to resident. Code is encrypted for admin redisplay, never logged; proof HMAC includes binding ID+OA+resident+occupancy+auth version+LINE ID. No raw LINE account edit can create a verified binding.
3. `line_room_policies`: `resident_id` PK/FK, `blocked` bool defaultfalse, `reason` varchar500 nullable, `updated_by` nullable FK, `updated_at`. Applied to both legacy and new code flows.
4. `line_admin_recipients`: auto `id`, `oa_id` FK, `label` varchar120, `is_owner` bool, `enabled` bool, `muted_categories` JSON, `line_user_id` varchar33 nullable, `code_hash` char64 nullable unique, `code_enc` text nullable, `expires_at` nullable, `claimed_at` nullable, `revoked_at` nullable, `created_by` FK, timestamps. Pending codes use OWNER-/ADMIN- plus128-bit random hex; TTL5/10minutes. Only claimed recipients receive notifications. Same OA+LINE deduplicated by application; one current owner per OA is serialized by registry lock.
5. `line_notice_outbox`: auto `id`, `oa_id` FK, `resident_id` nullable FK, `binding_id` nullable FK, `admin_recipient_id` nullable FK, `recipient` varchar33, `category` varchar20, `message_enc` text, `status` pending/processing/sent/failed, `attempts` unsigned default0, `retry_key` char36 unique, `claim_token` char64 nullable, `lease_until` nullable, `next_attempt_at`, `last_error` varchar200 nullable, `sent_at` nullable, timestamps. Binding lifecycle notices are permitted to inform the just-revoked account, contain generic status without bill/name data, and expire in24h. Admin notices must revalidate recipient enabled/mutes under the registry lock before sending.
6. Extend `notification_outbox`: `line_oa_id` bigint unsigned default0 FK, `line_binding_id` bigint unsigned nullable FK, generated `line_delivery_key` = COALESCE(line_binding_id,0); replace unique(bill_id,purpose) with unique(bill_id,purpose,line_delivery_key). Existing rows stay OA0/legacyrecipient. Pin OA/binding through retries and validate relationship; multiple recipients must not duplicate bill rows in listings.

Migration is `014_line_platform.sql` (013 already exists). Fresh schema/defaults/install bundle and requirements checks must include the new structures. No production migration or provider message is executed during implementation.

## Lock order

OA registry named lock → resident binding named lock → bill/payment/outbox or resident/occupancy rows. OA registry mutations and actual OA transport both hold the same lock, so disabling/deleting/rotating cannot race an outgoing private reply. Webhook wait is bounded0–1s by existing8s budget. Do not acquire registry while already holding a resident lock. No code may fall back to another OA when the intended one is unavailable.

## OA service contract

`LineOfficialAccountService(Application, ?Closure $identityTransport=null)` methods: `all(): array` (list rows), `get(int $id): array` (safe row), `credentials(int $id): array` (internal row with access_token/channel_secret, require enabled/nondeleted), `defaultId(): int`, `create(array $input,int $adminId): array`, `update(int $id,array $input,int $adminId): array`, `remove(int $id,int $adminId): array`, `setDefault(int $id,int $adminId): array`, `rotateRoute(int $id,int $adminId): array`, `test(int $id,int $adminId): array`, `byRouteToken(string $token): array`, `withRegistryLock(callable $callback,int $waitSeconds=12): mixed`, `touchWebhook(int $id,?string $error=null): void`.

Inputs snake_case matching storage except secrets `channel_access_token`, `channel_secret`, and explicit `*_clear` flags; blank secrets preserve existing values. Safe rows include id/name/slug/basic_id/description/channel_id/add_friend_url/enabled/is_default/deleted_at, secret configured flags+masked hints, `line_message_base` optional, `line_add_friend_url`, `webhook_url`, `line_binding_ready`, identity/last_seen/error and pending/bound counts. Active token create/rotation verifies fixed LINE bot-info endpoint and pins provider identity; optional injected transport is CLI test only. Legacy0 cannot be hard deleted; soft delete/disable supported, original legacy webhook root respects state and route rotation. Credential edits for0 update only LINE fields in integration_settings. Registry lock must be safely reentrant within the same service instance (balanced acquire/release).

## Binding service contract

`LineRoomBindingService(Application)` methods: `overview(): array` => rows+counts; `detail(int $residentId): array` => resident_id/full_name/room_code/blocked/reason/bound_count/pending_codes/bound_accounts/history; `issue(int $residentId,array $input,int $adminId): array` => code row+detail; `revokeCode(int $residentId,int $bindingId,int $adminId): array`; `revokeAccount(...)`; `revokeAll(int $residentId,int $adminId=0): array`; `block(int $residentId,string $reason,int $adminId): array`; `unblock(int $residentId,int $adminId): array`; `isBlocked(int $residentId): bool`; `consume(string $code,string $lineUserId,int $oaId): array` => resident_id/occupancy_id/binding_id/newly_bound; `recipients(int $residentId): array` => verified current new bindings, each id/oa_id/resident_id/occupancy_id/line_user_id; `verified(int $bindingId,string $lineUserId,int $oaId): ?array`; `revokeForIdentity(int $residentId): void` (caller owns locks/transaction).

Issue input `ttl_days`1–30 default7, `oa_id` optional defaultservice.defaultId, `replace_pending` defaulttrue. Legacy binding appears in detail as account id0/OA0 when verified; new pending code rows return exact code/deeplink/expiry for authorized admin only. Revoke account0 unlinks legacy only; revokeAll/block also invoke legacy unlink+pending revoke. New binding consumed on wrong OA fails. Same OA+LINE cannot belong to different current residents; old OA0 resident.line_user_id participates in duplicate checks. Do not set resident.line_user_id for new bindings. Detail history does not decrypt used/revoked codes. All mutations use registry→resident lock and strict audits inside transaction (synthetic internal Request acceptable with admin actor supplied if service has no Request argument). Lifecycle notices can be queued via separate root-owned notice service after or inside the transaction once contract exists.

## HTTP contracts

Normal `{ok,data,message}` envelope; all admin and owner may use dedicated LINE endpoints. API credentials never returned.

- GET/POST `/api/admin/line/oas`; GET/PUT/DELETE `/api/admin/line/oas/{id}`; POST `.../{id}/test`, `/default`, `/rotate-route`; GET `.../{id}/webhook-status`.
- GET `/api/admin/line/bindings`; GET `/api/admin/line/residents/{id}`; POST `.../{id}/codes` bodyissue; DELETE `.../{id}/codes/{bindingId}`, `.../{id}/accounts/{bindingId}`, `.../{id}/accounts`; POST `.../{id}/block` `{reason}`, `/unblock` `{}`.
- GET `/api/admin/line/recipients`; POST same `{oa_id,label,is_owner}`; GET/PUT/DELETE `.../recipients/{id}`; edit `{label,enabled,muted_categories}`. Issue/get includes pending code/deeplink only while valid. Categories booking/payment/billing/tenancy/maintenance/security/system.
- POST `/api/webhooks/line/oa/{routeToken}` and existing legacy webhook. Signed raw body + destination identity + OA-specific dedupe/limiter/reply token routing. Legacy route is valid only for OA0 and only until its route is rotated.

UI pages `/admin#line-oas` and `/admin#line-bindings`: OA CRUD/default/status/test/rotate plus admin recipient claims; room filters/search, multiple code rows with copy/deeplink/QR and individual revoke, multiple masked bound accounts, readonly history, block/unblock and confirmations. Existing resident/admin dialogs remain supported through compatibility adapters.
