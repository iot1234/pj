# การจองห้องพักรายวัน

ระบบรองรับห้องรายวันแยกจากห้องรายเดือน คิดราคาต่อคืนและรวมค่าน้ำไฟในค่าพัก ห้องหนึ่งใช้รูปแบบเดียวในแต่ละช่วง และเปลี่ยนรูปแบบไม่ได้ขณะมีผู้พัก การจอง ช่วงปิดขาย หรือคืนที่ยังกันไว้จากการเช็กเอาต์ก่อนกำหนด

## เริ่มใช้งาน

1. เจ้าของเข้าสู่ระบบ เลือก **เข้าส่วนงานรายวัน** → **ห้องรายวัน** → **เพิ่มห้องรายวัน** กรอกราคาต่อคืน จำนวนผู้พักสูงสุด และเงินประกันต่อการพัก (ใส่ 0 หากไม่เก็บ) ฟอร์มกำหนดประเภทรายวันไว้แล้ว
2. ลูกค้าเปิด `/daily` เลือกวันเข้า วันออก และจำนวนคน เลือกห้องแล้วตรวจราคา ก่อนกรอกชื่อและเบอร์ส่งจอง
3. ห้องถูกถือไว้ไม่เกิน 30 นาที ใบเสนอราคามีอายุไม่เกิน 10 นาที ทั้งสองอย่างสิ้นสุดก่อนถึงวันออกตามเวลาไทย เพื่อไม่ให้จองช่วงที่เข้าพักไม่ได้แล้ว ราคาและจำนวนคืนมาจากเซิร์ฟเวอร์ เช่น เข้า 10 ออก 12 เท่ากับ 2 คืน
4. รับเงินค่าพักและเงินประกันเต็มยอดก่อนยืนยัน รองรับสลิปพร้อมเพย์เมื่อบริการพร้อม หรือเจ้าของบันทึก **เงินสดที่รับแล้ว** สำหรับผู้พักหน้าหอที่ยังไม่ได้ออก QR
5. เปิด **จองรายวัน** เพื่อตรวจรายการและปฏิทิน เช็กอินในช่วงวันที่จอง และเช็กเอาต์เมื่อชำระครบและจัดการเงินประกันแล้ว
6. หลังเช็กเอาต์ ห้องขึ้น **รอทำความสะอาด** เจ้าของตรวจห้องแล้วกด **พร้อมใช้งาน** ก่อนรับผู้พักคนถัดไป

หน้าเจ้าของรองรับปิดขายห้องตามช่วงวันที่พร้อมเหตุผล และคืนเงิน/หักเงินประกันพร้อมเลขอ้างอิง การบันทึกคืนเงินหมายถึงบันทึกเงินที่เจ้าของคืนไปแล้ว ระบบไม่ได้สั่งโอนเงินออกจากบัญชีธนาคาร

ตารางเริ่มต้นรวมผู้พักที่ถึงวันออกหรือเกินกำหนดและยังไม่เช็กเอาต์ แม้ช่วงวันที่เลือกจะเริ่มวันนี้ หากมีข้อมูลมากกว่า 500 รายการ ให้กด **โหลดรายการเพิ่มเติม** เพื่ออ่านหน้าถัดไปตามตัวกรองเดิม

## ส่วนงานและรายรับที่แยกกัน

หลังเข้าสู่ระบบ หน้า **เลือกส่วนงาน** มีรายวันและรายเดือน เมื่อเข้าส่วนงานหนึ่ง เมนูจะแสดงเฉพาะงานของส่วนนั้น กลับหน้าเลือกส่วนงานเพื่อเปลี่ยนประเภท ห้องและการจองมีรายการของตนเอง ฟอร์มเพิ่ม/แก้ไขห้องไม่เปิดให้เปลี่ยนข้ามประเภท ภาพรวมรายวันนับการจองทั้งหมด ไม่ขึ้นกับหน้าตารางหรือช่วงวันที่ที่กำลังเปิด

- **รายรับรายวัน** แยกค่าห้อง เงินประกัน เศษยอดโอน เงินคืน และยอดหักประกัน การหักประกันไม่ใช่การรับเงินเพิ่ม ค่าห้องที่รับแล้วเป็นยอดก่อนหักเงินคืน; เงินคืนรายการยกเลิกไม่มีการเดาแบ่งสัดส่วนค่าห้องกับประกัน
- **รายรับรายเดือน** แยกค่าเช่า ค่าน้ำ ค่าไฟ รายการอื่นในบิล และเศษยอดโอน อ่านประวัติบิลรายเดือนเดิมเสมอ แม้ประเภทห้องปัจจุบันเปลี่ยนไป
- เลือกเดือนตามวันที่ระบบ **ยืนยันรับเงิน** และวันที่ **บันทึกคืนเงิน/หักประกัน** ไม่ใช่วันที่โอนหรือเดือนในบิล เงินที่ยังรอตรวจไม่รวมยอดรับ
- เงินเข้าออกสุทธิรายวันรวมเงินประกันและหักเงินคืน จึงไม่ใช่รายได้ค่าห้องหรือกำไร รายงานนี้ยังไม่คำนวณรายได้ตามวันที่เข้าพัก
- เงินประกันของรายการพักที่ยังดำเนินอยู่ ยอดเงินรอคืนของรายการสิ้นสุด และเงินยืนยันรับแล้วแต่การจองยังรอยืนยัน เป็นยอดปัจจุบันของทุกเดือน ไม่ใช่ยอดสิ้นเดือนที่เลือก

API ห้องแยกที่ `/api/admin/daily/rooms` และ `/api/admin/monthly/rooms` ตรวจประเภททั้งก่อนเขียนและหลังล็อกห้อง รายงานอยู่ที่ `/api/admin/daily/revenue?period=YYYY-MM` และ `/api/admin/monthly/revenue?period=YYYY-MM`; สรุปรวมทั้งเดือนและแบ่งหน้ารายการครั้งละ 200 รายการ API เดิม `/api/admin/rooms` อ่านเฉพาะรายเดือนโดยปริยาย หรือระบุ `rental_mode=daily` ได้ ระบบป้องกันสลิป/เลขธุรกรรมซ้ำยังตรวจร่วมทั้งสองประเภทเพื่อกันรับเงินซ้ำข้ามส่วนงาน

## การรับเงินและรายการที่ต้องตรวจ

- QR แสดงยอดโอนจริงที่รวมเศษสตางค์สำหรับระบุรายการ ให้โอนตามยอดที่แสดงเพียงครั้งเดียว
- การสร้าง QR รายวันต้องมีพร้อมเพย์และบริการตรวจสลิปพร้อมใช้งาน การรับเงินสดของเจ้าของทำงานได้โดยไม่ตั้งผู้ให้บริการภายนอก
- เมื่อออก QR แล้ว ระบบไม่เปิดให้เปลี่ยนเป็นรับเงินสดในรายการเดิม เพื่อหลีกเลี่ยงการรับซ้ำจาก QR ที่ยังโอนได้
- สลิปกำลังตรวจหรือผลยังไม่แน่นอนต้องตรวจรายการเดิม ห้ามชวนโอนซ้ำ เจ้าของเปิดหลักฐานและลองตรวจใหม่ได้
- ถ้าไฟล์หลักฐานหายหรืออ่านไม่ได้ เจ้าของกู้ด้วยไฟล์ต้นฉบับที่ตรงกับหลักฐานเดิม แล้วตรวจสลิปใหม่ได้ หากต้อง **พักการตรวจ** ให้ระบุเหตุผล ระบบเก็บประวัติไว้และยังไม่ถือว่าเงินเข้าหรือไม่เข้า จึงไม่เปิด QR หรือรับเงินสดซ้ำ ลูกค้าให้ติดต่อเจ้าของเพื่อตรวจหลักฐาน
- สลิปที่ถูกปฏิเสธเพราะส่งผิดรายการอาจตรวจใหม่กับรายการที่ถูกต้องได้ โดยตรวจยอด เวลา บัญชีปลายทาง และเลขธุรกรรมทั้งหมดอีกครั้ง สลิปที่กำลังตรวจ พักตรวจ หรือยืนยันเงินแล้วใช้ซ้ำข้ามรายการไม่ได้ ประวัติผลเดิมไม่ถูกลบ
- ผลตรวจเงินกับสิทธิ์ห้องแยกกัน ถ้าเงินเข้าหลังการจองหมดอายุหรือยกเลิก ระบบเก็บเงินรับไว้และแสดงงานคืนเงิน โดยไม่เอาห้องกลับจากผู้จองคนถัดไป
- เงินประกันต้องคืน หรือบันทึกยอดหักพร้อมเหตุผล ให้ครบก่อนเช็กเอาต์ เงินคืนรวมต้องไม่เกินเงินรับจริง
- ยอดโอนที่ชำระแล้ว หรือคำขอที่หมดอายุ/ยกเลิกและไม่มีสลิปรอตรวจ ถูกพักไว้ 7 วันก่อนคืนช่องยอด ระบบเก็บ QR และหลักฐานเก่าไว้ครบ ไม่จับคู่เงินเข้ากับการจองจากยอดอย่างเดียว: ลูกค้าต้องส่งสลิปด้วยสิทธิ์ของการจองนั้น พร้อมตรวจยอด เวลา บัญชีปลายทาง และเลขธุรกรรมซ้ำ
- ช่วงเศษสตางค์มี 99 ช่องต่อยอดฐานเดียวกัน ขณะช่องถูกใช้งานหรืออยู่ในช่วงพักยอด หากเต็มให้ติดต่อเจ้าของเพื่อรับเงินสดในรายการใหม่ที่ยังไม่ได้ออก QR ช่องที่พ้นเงื่อนไข 7 วันกลับมาใช้ได้โดยไม่แก้หลักฐานเก่า

## การกู้คืนเมื่อเครือข่ายขาด

การส่งจองและงานเจ้าของเก็บรหัสคำขอเดิมไว้ในแท็บ แม้รีโหลดหน้า หากไม่ทราบผล หน้าจอให้ตรวจ/ส่งคำขอเดิมแทนสร้างรายการใหม่ การรับเงินสดหรือคืนเงินที่ไม่ทราบผลจะล็อกข้อมูลเดิม ไม่ให้รับหรือคืนเงินจริงซ้ำ ผลค้นที่ยังไม่พบคำขอไม่ได้แปลว่าคำขอล้มเหลว เพราะคำขอเดิมอาจยังทำงานอยู่

การส่งสลิปที่ไม่ทราบผลต้องส่งไฟล์เดิมที่มีเนื้อหาเดิมซ้ำ ระบบตรวจลายนิ้วมือไฟล์ก่อนส่ง ไม่ถือว่ารายการสลิปเก่าที่ถูกปฏิเสธเป็นผลของคำขอใหม่ และไม่แนะนำให้โอนอีกครั้ง หากเบราว์เซอร์เก็บข้อมูลแท็บไม่ได้ จะแจ้งเตือนให้คงแท็บไว้และติดต่อเจ้าของก่อนทำรายการเงินใหม่

ลูกค้าเปิดรายละเอียดด้วยสิทธิ์เฉพาะการจองที่เก็บในแท็บเบราว์เซอร์ ไม่มีการค้นประวัติด้วยชื่อหรือเบอร์อย่างเดียว หากล้างข้อมูลหรือเปลี่ยนเครื่อง ให้แจ้งเลขการจองกับเจ้าของเพื่อดูสถานะและส่งหลักฐานผ่านหลังบ้าน การจองที่หมดอายุ/ยกเลิกยังส่งหลักฐานเงินที่โอนไปแล้วให้ตรวจและจัดการคืนเงินได้

LINE แจ้งเจ้าของที่ผูกบัญชีและเปิดหมวดแจ้งเตือนไว้ ผ่าน outbox เดิมโดยไม่ใส่ชื่อ เบอร์ หรือข้อมูลการเงินของลูกค้าในข้อความ รายวันยังไม่ส่ง push เข้า LINE ของลูกค้าโดยตรง

## ติดตั้งและอัปเกรด

ฐานใหม่ใช้ `database/install.sql` หรือ `database/schema.sql` ตามด้วย `database/defaults.sql` ตามคู่มือเดิม ไม่ใช้ installer ทับฐานที่มีข้อมูล

ฐานเดิมต้องผ่าน migration 017 ก่อน สำรองข้อมูลและทดสอบ restore หยุด web traffic, worker และงานออกบิล จากนั้นใช้บัญชี schema owner import ตามลำดับ:

1. `database/migrations/018_daily_bookings.sql`
2. `database/migrations/019_daily_payments.sql`
3. `database/migrations/020_daily_review_fixes.sql`

ทั้งสามไฟล์ self-contained และรองรับรันซ้ำเมื่อยืนยันสภาพแวดล้อมแล้ว 018 เพิ่มห้อง/การจองรายวันโดยตั้งห้องเดิมเป็นรายเดือน 019 สร้างทะเบียนหลักฐานและยอดโอนร่วม พร้อม backfill รายเดือน 020 อัปเกรดฐานที่เคยติดตั้ง 018/019 ให้รองรับกู้หลักฐาน พักตรวจ และกฎป้องกันใช้หลักฐานซ้ำฉบับที่แก้แล้ว หากประวัติขัดแย้งหรืออัปเกรดไม่ครบ migration จะไม่ประกาศว่าพร้อมใช้งาน

ถ้าติดตั้ง 018/019 รุ่นก่อนรอบตรวจนี้แล้ว ให้ใช้ 020 ก่อนเปิด source รุ่นนี้ ไม่ใช้ installer ทับฐานเดิม

Deploy source ที่ตรงกับ migrations แล้วรัน:

```powershell
php scripts/build_install_sql.php --check
php scripts/check_requirements.php --db --schema-audit
```

`--schema-audit` ใช้บัญชี schema owner ชั่วคราวเพื่อรับรอง trigger bodies ตาม canonical SQL หลังตรวจ ให้ web/worker กลับไปใช้บัญชี runtime เฉพาะ SELECT/INSERT/UPDATE และตรวจ `/healthz.php` ก่อนเปิด traffic

Worker เดิมปล่อย hold รายวันเป็นชุดและบันทึก audit ส่วนการค้นหาห้องยังตัด hold ที่หมดอายุด้วยเวลาฐานข้อมูล แม้ worker หยุดชั่วคราว

หน้ามิเตอร์รายเดือนแยกห้องรายวันออกจากรายการที่ต้องจดใหม่ ประวัติมิเตอร์และบิลรายเดือนที่เคยมีอยู่ยังอ่านได้ หากห้องเปลี่ยนเป็นรายวัน ประวัติมิเตอร์จะอ่านอย่างเดียว ค่าน้ำไฟของผู้พักรายวันรวมอยู่ในค่าพัก การแก้ข้อมูลห้องใช้รุ่นข้อมูลล่าสุดและแจ้งเมื่อมีผู้แก้พร้อมกัน แทนเขียนทับข้อมูลเก่า

## ขอบเขตและการทดสอบ

จองล่วงหน้าได้ 365 วัน ครั้งละ 1–90 คืน ผู้พักไม่เกินความจุห้อง รองรับราคาเดียวต่อคืน เงินประกัน และชำระเต็มยอด การต่อคืน ย้ายห้อง ราคาเทศกาล แบ่งชำระ และการใช้ห้องสลับรายเดือน/รายวันในช่วงเดียวกันยังเป็นงานเพิ่มเติม

ใช้ `tests/daily_booking_unit.php`, `tests/daily_booking_mysql.php`, `tests/daily_payment_mysql.php`, `tests/daily_schema_fault_mysql.php` และ `tests/daily_migration_mysql.php` ตาม guard ของแต่ละไฟล์ เฉพาะ MySQL แยกที่ชื่อฐานขึ้นต้น `appj_` สำหรับทดสอบเท่านั้น ชุด provider ใช้ transport จำลอง ไม่โอนเงินจริงหรือส่ง LINE จริง

`tests/browser-daily.mjs` ตรวจหน้าจอจริงกับฐาน fixture ส่วน `tests/browser-daily-ui.mjs` ตรวจการโหลดและหน้าจอกับ API จำลอง รายละเอียดผลรอบพัฒนาอยู่ใน `docs/DAILY_QA_2026-10-09.md`
